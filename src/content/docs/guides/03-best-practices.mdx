## Credential Security

### API Key

Your API token is transmitted in plain text with every request via the `Authorization` header. It must be treated with the same level of care as a password.

**Recommendations:**
- Never commit it to a version control system (Git or otherwise)
- Store it in an environment variable or a secret manager (Vault, AWS Secrets Manager, etc.)
- Never expose it on the client side (browser, mobile application)

<Aside type="note">
Barestho does not store your tokens in plain text: they are hashed on our end. If lost, it is impossible to recover them. You can request a new one from the Barestho team at any time, without any service interruption.
</Aside>

<Aside type="tip">
It is possible to have **multiple access tokens** simultaneously, which allows for rotation without downtime, for example.
</Aside>

A token may have an expiry date. An expired token gets `401 AUTHENTICATION_FAILED` with the message `Expired token, please use another one.`: rotate before the expiry.

Do not retry a request that failed with `401`: fix the credentials first. After 20 failed authentications in 15 minutes, every request from your IP address gets `429 RATE_LIMITED` until the end of the window, valid credentials included (see [Authentication](/partnership-documentation/guides/01-api-communication#authentication)).

---

### Webhook Token

The `auth_token` generated by Barestho when a webhook is created is used to verify the authenticity of incoming requests.

**Recommendations:**
- Store it securely, just as you would with your API key

<Aside type="note">
Barestho encrypts webhook tokens at rest.
</Aside>

## Reliability

Networks fail and events can be missed. These habits keep your data right:

- **Retry writes safely.** Send an `Idempotency-Key` header (a new UUID per operation) with the reservation creation and updates, including the status actions. A retry with the same key returns the first answer instead of creating a duplicate or failing on an action already applied. See [Retry Safely](/partnership-documentation/guides/05-manage-reservations#retry-safely).
- **Book from the bookable slots.** `GET /availabilities/slots/` lists only the slots that can be booked now for your party size. See [Bookable Slots](/partnership-documentation/guides/06-read-availabilities#bookable-slots).
- **Catch up with an incremental sync.** Webhooks can arrive late, twice or out of order. Read the reservations changed since your last sync with `updated_at__gte`. See [Incremental Sync](/partnership-documentation/guides/05-manage-reservations#incremental-sync).
- **Deduplicate webhook events** with `X-Webhook-Request-Id`, and ignore an event older than the `updated_at` you hold. See [Delivery and Retries](/partnership-documentation/guides/02-creating-webhooks#delivery-and-retries).
- **Respect the rate limit.** On `429`, wait for `Retry-After` seconds. See [Rate limiting](/partnership-documentation/guides/01-api-communication#rate-limiting).
- **Send datetimes with a timezone** (`Z` or `+02:00`). Filters refuse a date and time without one.
